Tuning the retrieval pipeline without rewriting it

This system is a chain of six swappable stages. Some you change with an .env line and a restart; some need code. This is the map of which is which, what each stage is actually doing in machine-learning terms, and how to prove a change was an improvement.

The generation stage is a config change because of a deliberate design choice. One file, app/llm/base.py, defines the contract every model backend must satisfy — an async generate() and an is_available() check. One file, app/llm/factory.py, is the only place a concrete backend is picked. Everything downstream — the RAG pipeline, the intent router, the API routes — depends on the interface, never on AnthropicProvider or OpenAIProvider directly.

the takeaway Because nothing imports a provider class directly, moving from the local model to a cloud API is an .env edit plus a process restart. No code touches the pipeline.

The procedure

  1. Get an API key from the provider.
  2. Edit .env — for example, to run Claude Sonnet:
    .env
    # was: LLM_PROVIDER=local  /  LLM_MODEL=qwen2.5:3b
LLM_PROVIDER=anthropic
LLM_MODEL=claude-sonnet-5
ANTHROPIC_API_KEY=sk-ant-…
  3. Restart the server. The provider is constructed once at startup (app/main.py lifespan → app.state.llm); a running process will not pick up the change.
  4. Verify:
    terminal
    curl -s localhost:8000/health | jq '{llm_provider, llm_model, llm_available}'
# → {"llm_provider":"anthropic","llm_model":"claude-sonnet-5","llm_available":true}

curl -s localhost:8000/ask -H 'content-type: application/json' \
  -d '{"question":"Hadley v Baxendale — what damages rule?","top_k":5}'
on record in CODEBASE_CONTEXT §5 Groq and Google Gemini are geo-blocked from the network this runs on, which is why the default is local. A cloud key still needs a route that resolves — a provider that isn't blocked, or an outbound proxy.

Per-request override, no restart

POST /ask and POST /assistant accept an optional model field, and GET /models lists what's reachable. For the local provider that's everything in ollama list; for a cloud provider it reports the configured model. Useful for a quick A/B without editing .env — but the provider itself (anthropic vs openai vs local) is still fixed at startup.

Adding a provider that isn't wired yet

Say Cohere, or Vertex, or a bespoke endpoint. Copy one of the ~40-line files in app/llm/, implement generate() and is_available() against base.py, and add one line to _PROVIDERS in factory.py. Nothing else changes.

Rough cost per question

One assistant request is 1–2 model calls. The RAG call sends roughly 1.5–2.5k input tokens (five ~900-char chunks plus the prompt) and generates ~300–800. Indicative first-party Anthropic rates:

3 Swapping the embedding model — the harder one

The embedding model defines the vector space the whole index lives in. Vectors written by model A are meaningless to model B, so you cannot swap it in place — you re-embed the corpus. Three things must move together:

VarRead inMust equal
EMBEDDING_MODELconfig.py → embeddings.pya model fastembed supports
EMBEDDING_DIMdb/models.py — directly from os.environ, not via Settingsthat model's output dimension
EMBEDDING_PREFIXESembeddings.py directly1 for the e5 family, 0 for bge / paraphrase-multilingual
easy to get wrong EMBEDDING_DIM bypasses config.py entirely. If it doesn't match the model, the mismatch surfaces as an insert or query error against the fixed-width pgvector column — not a clear message. Current tree: paraphrase-multilingual-MiniLM-L12-v2, 384-dim, prefixes off. .env.example proposes intfloat/multilingual-e5-large, 1024-dim, prefixes on — better Persian, slower.
terminal — after editing all three vars
python -m scripts.ingest data/farsi --reset   # re-chunk + re-embed the corpus
python -m scripts.extract --reset             # rebuild structured Entry rows (uses the LLM)
python -m scripts.eval                        # confirm retrieval didn't regress

Using a cloud embedding API

embeddings.py currently hardwires fastembed (local ONNX, no GPU). To call OpenAI text-embedding-3-large, Cohere embed-v4, or Voyage, you replace three functions — _model(), embed_passages(), embed_query() — with API calls that return the same list[float], and set EMBEDDING_DIM to the API model's dimension. The retriever, the schema, and the pipeline are untouched. This is a genuine code change, but a contained one.

4 What each stage is actually doing

Enough of the machine learning to reason about a change instead of guessing at it.

Embedding: text → a point in space

A transformer encoder reads a passage and emits a fixed-length list of numbers — here 384 of them. It was trained so that passages with similar meaning land close together and unrelated ones land far apart (contrastive training on labelled pairs). A multilingual model puts all languages in one shared space, which is the reason a Persian query can retrieve a Persian passage at all. Nothing here is generative; it's a fixed function from string to vector.

why the prefixes flag exists e5-family models were trained with the literal strings "query: " and "passage: " prepended, so they learned two asymmetric roles. Feed them text without that convention and retrieval quality drops. Models outside that family never saw the prefixes and should run with EMBEDDING_PREFIXES=0.

Retrieval: three stages, fused then re-ranked

retriever.py now runs a hybrid pipeline. Stage 1a embeds the query and asks Postgres (pgvector) for the nearest chunks by cosine distance — the angle between the two vectors. Stage 1b runs a Postgres full-text query over the same chunks (an OR of the query's word tokens against a stored tsvector column), which catches exact terms — names, case numbers, statute refs — that a blurry embedding misses. The two ranked lists are fused with Reciprocal Rank Fusion (RRF_LEX_WEIGHT discounts the noisier lexical vote). Stage 2 takes the fused top RERANK_TOP and re-scores each (query, chunk) pair with a multilingual cross-encoder (jinaai/jina-reranker-v2-base-multilingual) that reads both texts together; its top k is the final result. Every stage has an env toggle (HYBRID=0, RERANK=0) so scripts/eval.py can measure each one's contribution.

measured on eval/farsi.jsonl (17 cases) vector-only → hybrid → hybrid+rerank: hit@1 0.41 → 0.59 → 0.88, MRR 0.63 → 0.76 → 0.94, cov@5 0.60 → 0.85 → 0.95. The reranker is the biggest single lever; the lexical stage is what fixed the name/number queries.

Chunking: why the corpus is cut up first

Documents are sliced into ~900-character windows with 150 of overlap before embedding, because a single vector loses fidelity over long text, and because you want to hand the model the relevant paragraph, not a whole case file. Fixed-size windows are the naive version — they cut mid-sentence and ignore legal structure (ماده, بند, تبصره). Structure-aware chunking is a known gap, flagged in chunk_text() itself.

Generation: grounded, not looked-up

The top 5 chunks are numbered [1]…[5] and pasted into a prompt with a system instruction: answer only from these excerpts, cite the bracket number for every claim, reply in the question's language. The model is doing conditioned text generation. It is not retrieving anything itself — everything it can legitimately cite has to be in those five chunks. That constraint is the entire point of RAG: the model can't invent a statute or a holding, because it was only given the retrieved text.

what this system does not do No agent loop, no multi-hop, no tool calls, no query rewriting. One retrieve, one generate. The "assistant" layer adds a single-shot intent classifier in front (query / archive / analytics) — still one pass, no planning. Be precise about this when scoping work.

5 Proving a change helped

Every knob in §2–§4 is a hypothesis. scripts/eval.py (and the mirrored POST /eval) scores retrieval against eval/farsi.jsonl:

MetricQuestion it answers
hit@1 / hit@3 / hit@kdid any expected document land in the top-N?
MRRhow high did the first expected document rank? (1 / rank, averaged)
cov@kfor multi-document questions, what fraction of expected docs were retrieved?

These measure retrieval only. --ask also runs generation and prints answers for manual reading — there is no automatic answer scoring yet (that gap is where an LLM-as-judge would go: send both answers plus the gold context to a strong model and ask which is better grounded).

The experiment loop

  1. python -m scripts.eval → write down the baseline numbers.
  2. Change one thing: embedding model, chunk size, top_k, prefixes, the answer prompt.
  3. If embeddings or chunking changed: python -m scripts.ingest data/farsi --reset.
  4. python -m scripts.eval → compare. Keep or revert.
highest-leverage move Grow eval/farsi.jsonl. Each line is {q, expect:[source-substring], kind, want_all?}. Twenty to fifty real questions from how lawyers actually phrase things is worth more than any single model swap, because without them you're tuning blind.

6 When a config change isn't enough

ChangeWhereEffortExpected payoff
Hybrid retrieval (BM25 + vector) done — retriever.py, fused with RRF; the tsvector column is a stored generated column on chunks — delivered: name/number queries went from cov@5 0.60 → 0.85
Re-ranking done — rag/rerank.py, multilingual cross-encoder over the fused shortlist — delivered: hit@1 0.59 → 0.88, MRR 0.76 → 0.94
Upgrade embeddings to e5-large (1024-d) scripts/upgrade_embeddings.py — model is downloaded; needs a .pgdata rebuild + re-ingest + re-extract small (one script) incremental now that rerank carries most of the precision
Structure-aware chunking ingest.py::chunk_text — split on legal structure and headings instead of a fixed window small–medium medium
Metadata filters (court, date, jurisdiction) capture metadata at ingest + add a WHERE clause to the retrieval query medium large once the corpus is big
Fine-tune the embedding model on Persian legal pairs out-of-tree: build a (query, relevant-passage) dataset, train with sentence-transformers large only worth it once off-the-shelf multilingual models measurably plateau

7 Filling the knowledge gap — a path for the team

Work through these in order. Each is a concept plus something concrete to do with it.

  1. Dense retrieval & vector search — cosine similarity, embedding spaces, approximate-nearest-neighbour indexes (HNSW). Read the pgvector README and the sentence-transformers "semantic search" documentation; then run scripts/eval.py and change top_k to feel the trade-off.
  2. Chunking strategies — fixed vs recursive vs structure-aware vs semantic. Experiment directly in chunk_text() and measure.
  3. RAG fundamentals — the original retrieval-augmented generation paper (Lewis et al., 2020) for the core idea; any current "advanced RAG" survey for the vocabulary: query rewriting, HyDE, hybrid search, re-ranking, fusion.
  4. Evaluation — retrieval metrics (hit rate, MRR, nDCG) vs answer metrics (faithfulness, answer relevance). Look at RAGAS and TREC-style ir_measures. Understand why LLM-as-judge is useful and where it's biased.
  5. Re-ranking — bi-encoder (fast, what we have) vs cross-encoder (slow, accurate). Read the BGE and mxbai reranker model cards.
  6. Grounded generation & prompting — the Anthropic and OpenAI prompting guides; citation and faithfulness techniques; how context position affects what the model uses ("lost in the middle").
  7. Persian NLP specifics — text normalization (ZWNJ, Arabic vs Persian yeh/kaf), the Hazm and Parsivar libraries, and how multilingual-e5 scores on Persian retrieval benchmarks.
  8. Production concerns — vector-DB scaling and index types, caching embeddings, latency and cost budgets, when to move off embedded Postgres.
fastest way into this codebase specifically Read docs/CODEBASE_CONTEXT.md end to end. Then trace one request each way: a question through pipeline.py → retriever.py → embeddings.py, and an assistant turn through orchestrator.py. That's ~300 lines and covers the whole system.

8 Getting a new developer running

terminal
uv venv --python 3.12            # pgserver needs Python ≤ 3.12
uv pip install -r requirements.txt
cp .env.example .env             # then edit — see §2 / §3

# local baseline (no API keys, works offline):
ollama pull qwen2.5:3b
python -m scripts.ingest data/farsi
python -m scripts.extract        # ~15 s/doc, uses the LLM
scripts/serve.sh                 # API + UI on :8000

python -m scripts.eval           # baseline retrieval numbers

To develop against a cloud model instead, set .env per §2 and skip the ollama pull. Two things to know before you change data models: there are no tests and no migrations in the tree — the schema is create_all on startup, so a model change needs a manual DB rebuild (rm -rf .pgdata then re-ingest).

before experiments multiply This directory isn't a git repository yet. git init, push it to GitHub, and run each experiment on its own branch — the eval numbers in the commit message become the record of what worked.
