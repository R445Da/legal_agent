# v3 — provenance, agency, conversation, live CI

v2 answered questions. v3 answers them *and shows its work*: every answer
carries a checked provenance block, the model can research the archive with
read-only tools over several turns, filing a case can happen as a
conversation, similar past cases come out of the case graph with the reason
they resemble the question, and the archive emits signed webhooks while the
dashboard shows this repository's CI pipeline live.

Everything runs offline with `LLM_PROVIDER=mock`, which is what CI and the
demo scripts use.

---

## 1. Provenance-first tool loop

`app/rag/tools.py` holds the read-only tool surface (`search_law`,
`search_cases`, `similar_cases`, `entity_profile`, `case_graph`,
`graph_expand`, entries and documents). One `EvidenceLedger` spans a whole
answer: each tool result appends numbered evidence `[1]..[n]`, the numbers
never restart between rounds, and the model is told to cite them.

On providers that support it (`anthropic`, `openai`, `groq`) the loop uses
**native `tool_result` turns** — the transcript keeps real assistant
tool-call turns and real tool-result turns, so the model sees its own calls
rather than a flattened string. `TOOL_LOOP=text` forces the older
"append results as text" loop, which `local` and `mock` always use.

`app/rag/provenance.py` closes the loop with plain code instead of trust:
`verify_citations()` parses the `[n]` the model actually wrote, checks each
names real evidence, splits the answer into claims and marks the ones with no
valid citation. Deterministic on purpose — the mock model verifies exactly
the way a real one does. Every answered question becomes one row in
`assistant_answers` (`GET /answers`, `GET /answers/{id}`) and emits an
`answer.created` event.

### The provenance block

```json
{
  "version": 1,
  "intent": "law",
  "provider": "anthropic",
  "model": "claude-opus-5",
  "evidence": [
    {"n": 1, "kind": "law",  "id": "l1", "cite": "مادهٔ ۳۰ قانون بیمه",
     "label": "ماده: مادهٔ ۳۰ قانون بیمه", "score": null},
    {"n": 2, "kind": "case", "id": "c-1", "cite": "1402009988",
     "label": "پرونده: 1402009988", "score": 0.91}
  ],
  "tool_trail": [
    {"seq": 1, "tool": "search_law", "summary": "search_law(query='ماده ۳۰') → 3 ماده",
     "ms": 12, "evidence_ns": [1]}
  ],
  "grounding": {"cited": [1, 2], "valid": [1, 2], "invalid": [],
                "coverage": 1.0, "status": "ok", "unsupported_claims": []},
  "usage": {"calls": 2, "input_tokens": 2310, "output_tokens": 410,
            "cache_read_tokens": 2048, "cache_write_tokens": 0, "latency_ms": 1830},
  "latency_ms": 1830,
  "created_at": "2026-09-12T14:22:39+00:00"
}
```

`kind` is one of `law | case | entry | document | chunk`. `status` is `ok`
(coverage ≥ 0.8 and no dangling numbers), `partial`, or `unsupported`; the
per-claim list stays out of the block and only `unsupported_claims` rides
along. `PROMPT_CACHE=1` marks the system prompt and tool list for caching,
which is where `cache_read_tokens` comes from.

## 2. The `agent` intent — «پژوهش عاملی»

`app/rag/agent.py` is a fourth answer route beside `law` / `cases` / `query`:
instead of one fixed retrieval it lets the model choose what to look up over
a few rounds, then answers from the ledger. Never auto-routed — pick it in
the «نوع پیام» selector, send `intent="agent"` to `POST /assistant`, or set
`AGENT_FOR_QUERY=1` to route plain questions through it. The result carries
the same provenance block as every other route.

## 3. Conversation mode — «گفتگویی»

`app/rag/conversation.py` turns filing into a dialogue. The assistant says
what it extracted, names what is missing, and asks for it **in the chat**
instead of showing a form; a reply patches the draft (`entities.case_number`
and friends), and «تأیید» commits. `CONVERSATION_MAX_ROUNDS` caps the
rounds before it commits with whatever it has.

```
POST /runs                {"text": "...", "mode": "conversation"}   → run + question
POST /runs/{run_id}/reply {"text": "شماره پرونده: ۱۴۰۲۰۰۱۲۳۴"}      → next question
POST /runs/{run_id}/reply {"text": "تأیید"}                          → status: committed
```

The run stops at `awaiting_input` between turns; a reply to a finished run is
a 409.

## 4. Similar past cases through the graph

`app/rag/similar.py` expands a case's neighbourhood in the graph — shared
articles, shared parties, same court, same case type, existing `SIMILAR_TO`
links — and scores candidates. Each item carries `why` (Persian reasons:
«استناد مشترک به قانون بیمه — مادهٔ ۳۰», «طرف مشترک: …») and `path`, a list
of graph paths, each a list of nodes with relation nodes between them:

```json
"path": [[{"type": "law", "id": "l1", "label": "قانون بیمه — مادهٔ ۳۰"},
          {"relation": "CITES", "relation_fa": "استناد به", "dir": "in"},
          {"type": "case", "id": "c-1", "label": "بازیافت خسارت…"}]]
```

`lessons` tallies how those cases ended («چه چیزی جواب داد / نداد») and, with
`SIMILAR_STAGE_LLM=1`, one extra call writes the comparative `advice`
paragraph. `SIMILAR_STAGE=0` turns the whole stage off; `SIMILAR_STAGE_LLM=0`
keeps the list and skips the call.

## 5. Webhooks and live CI

`app/rag/hooks.py` is a transactional outbox: `emit()` writes one
`webhook_deliveries` row per matching subscription **inside the caller's
transaction**, so a delivery exists only if the fact it reports committed.
`drain()` sends what is due with `FOR UPDATE SKIP LOCKED`, so the API timer
and the Streamlit app never send the same delivery twice; failures back off
`5s · 2^attempts` and die after 6 attempts.

Events: `run.step`, `run.status`, `entry.committed`, `answer.created`,
`ping`. Subscriptions match exactly, by prefix (`run.*`), or `*`.

```
POST   /hooks                     {"url": ..., "events": ["*"], "description": ...}  → incl. secret
GET    /hooks                     ·  DELETE /hooks/{id}  ·  POST /hooks/{id}/test
GET    /hooks/deliveries          ?subscription_id=&status=
```

Envelope and headers:

```json
{"id": "<delivery uuid>", "event": "entry.committed",
 "created_at": "2026-09-12T14:22:39+00:00", "attempt": 1, "data": { ... }}
```

| Header | Meaning |
| --- | --- |
| `X-Legal-Event` | the event name |
| `X-Legal-Delivery` | delivery id — the same on every retry, use it to deduplicate |
| `X-Legal-Timestamp` | when this attempt was sent |
| `X-Legal-Signature-256` | `sha256=` HMAC-SHA256 of the raw body under the subscription's secret |

`WEBHOOK_ALLOWED_HOSTS` optionally restricts destination hosts (empty = any,
fine for a laptop demo, not for a public deployment).

### CI events

`app/rag/ci.py` stores three sources in `ci_events` and folds them into
runs → jobs → stages:

1. GitHub's own `workflow_run` / `workflow_job` webhooks at `POST /hooks/github`,
   verified against `GITHUB_WEBHOOK_SECRET` (503 while unset);
2. stage reports from `scripts/ci_status.sh` inside the workflow at
   `POST /ci/status` (auth: `CI_STATUS_TOKEN`, falling back to `API_TOKEN`;
   the script is a no-op unless `CI_STATUS_URL` is set);
3. `scripts/replay_ci.py`, which replays recorded or synthesised runs.

Redelivery of the same `delivery_id` is ignored. Read them back with
`GET /ci/events` (or `GET /ci/events/stream`, SSE).

```bash
python -m scripts.capture_ci --repo R445Da/legal_agent --runs 3   # real runs → fixtures
python -m scripts.replay_ci --synthesize --run-number 9 --branch v3 --fail-at build
python -m scripts.replay_ci --via github --secret "$GITHUB_WEBHOOK_SECRET"
python -m scripts.hook_sink --port 8099 --secret <secret from POST /hooks>
BASE=http://127.0.0.1:8000 API_TOKEN=… scripts/demo_hooks.sh       # the whole outbound demo
```

## 7. Demo stages

`app/demo/stages.py` keeps the demo as data: ordered `Stage`s, each with a
few `StagePrompt`s (text, forced intent, run mode, and what the answer must
contain). The chat offers them as chips when empty and walks a stage prompt
by prompt; the gallery lists them; `scripts/demo_stages.py` runs them all and
checks the expectations, so the demo script *is* the acceptance test
(`tests/test_stages.py` runs the same thing on the mock provider).

Stages: `law_lookup`, `precedents`, `agent_research`,
`conversational_filing`, `archive_analytics`, `ci_live` (UI only, no prompts).

## 8. New environment knobs

| Variable | Default | What it does |
| --- | --- | --- |
| `TOOL_LOOP` | `native` | `native` = multi-turn `tool_result` turns where the provider supports them; `text` = the older append-as-text loop |
| `PROMPT_CACHE` | `1` | mark the system prompt + tool list for prompt caching (Anthropic) |
| `AGENT_FOR_QUERY` | `0` | route plain «query» questions through the tool-using agent |
| `SIMILAR_STAGE` | `1` | after an answer, find resembling past cases through the graph |
| `SIMILAR_STAGE_LLM` | `1` | spend one extra call on the comparative advice paragraph |
| `CONVERSATION_MAX_ROUNDS` | `6` | question/answer rounds before conversation mode commits anyway |
| `WEBHOOK_ALLOWED_HOSTS` | empty | comma-separated destination allow-list for outbound webhooks |
| `GITHUB_WEBHOOK_SECRET` | empty | secret for `POST /hooks/github`; the receiver is 503 while unset |
| `CI_STATUS_TOKEN` | empty | bearer token for `POST /ci/status`; falls back to `API_TOKEN` |
| `CI_STATUS_URL` | unset | where `scripts/ci_status.sh` posts; unset = the script does nothing |

## 9. Running the demo and the tests

```bash
# against a running API
python -m scripts.provenance_probe "ماده ۳۰ قانون بیمه چه می‌گوید؟" --intent law
python -m scripts.provenance_probe "وکیل رضا کریمی در چه پرونده‌هایی بوده؟" --intent agent
python -m scripts.conversation_probe --reply "شماره پرونده: ۱۴۰۲۰۰۱۲۳۴" --reply "تأیید"
scripts/check.sh                       # every endpoint, PASS/FAIL per check

# no API needed
python -m scripts.demo_stages                       # all stages, exits 1 on a failed expectation
python -m scripts.demo_stages --stage law_lookup
python -m scripts.ui_smoke                          # renders all 19 Streamlit sections
pytest -q -m "not db"                               # unit: tool loop, signing, verifier
pytest -q -m db                                     # against the embedded cluster in PG_DATA_DIR
```

Both probes exit non-zero on a bad result (`unsupported` grounding, a run
that never committed), so they double as smoke checks. Offline env for any
of the above:

```bash
LLM_PROVIDER=mock LLM_MODEL=rules-v1 ROUTER_MODEL=mock::rules-v1 \
EMBEDDING_MODEL=hash://384 EMBEDDING_DIM=384 EMBEDDING_PREFIXES=0 RERANK=0 STT=0 \
PG_DATA_DIR=.pgdata-test python -m scripts.demo_stages
```

## 10. v2 → v3

| | v2 | v3 |
| --- | --- | --- |
| Tool loop | one retrieval, one generation; tool results appended as text | native `tool_result` turns, several rounds, one evidence ledger across them |
| Provenance | «this is the context I used» | numbered evidence + tool trail + citation verdict, persisted in `assistant_answers` |
| Caching | none | `PROMPT_CACHE=1` on the system prompt and tool list; cache tokens reported in `usage` |
| Structured output | JSON mode for extraction and routing | same, plus a typed provenance block on every answer and typed demo stages as data |
| HITL | form-based approval gates in the pipeline | conversation mode: the assistant asks in the chat, a reply patches the draft, «تأیید» commits |
| Graph | case graph browsable per case | graph-expanded similar cases with `why` / `path`, outcome lessons, comparative advice |
| Observability | run rows and step events | + signed outbound webhooks through a transactional outbox, inbound CI events, live pipeline panel, design gallery |
